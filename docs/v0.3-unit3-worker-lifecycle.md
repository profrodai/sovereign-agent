# v0.3 Unit 3 — worker lifecycle

Unit 3 separates provider invocation from worker runtime management. The
provider-independent `WorkerBackend` contract is now `prepare(request)`,
`execute(handle, invocation)`, and `close(handle, preserve)`, using immutable
`WorkerRequest` and `InvocationSpec` values plus explicit `RuntimeHandle`,
`ExecResult`, and `CloseResult` results.

`ExecutionLifecycle` records forward-only states, supports execution-local
cancellation, bounds cooperative and forced teardown, and reports stable
terminal reasons for aborts, timeout classes, provider/worker failures,
isolation failures, invalid structured output, verification, delivery, and
business-verification failures. Failure preservation retains session artifacts;
it never leaves a live worker process behind.

The built-ins now have distinct responsibilities:

- `BareWorker` executes in process.
- `SubprocessWorker` provides process separation only.
- `OSIsolatedWorker` composes `SubprocessWorker` with the existing Landlock or
  sandbox-exec policy.
- `DockerWorker` remains discoverable as unavailable and refuses at prepare
  time, before any invocation starts.

Capability probes use the Unit 1 `CapabilityManifest` and `EvidenceLevel`
contracts. A request for filesystem or network isolation fails closed unless
the selected backend can report that enforcement as available with
`EvidenceLevel.ENFORCED`. Landlock filesystem enforcement qualifies; its
network restriction does not. sandbox-exec qualifies for both.

The portable lifecycle, registry/relay, and release contracts are tested on
Linux, macOS, and Windows. Isolation enforcement is narrower by design:
Landlock is supported on qualifying Linux kernels and `sandbox-exec` on
qualifying macOS hosts. Windows exercises process-only lifecycle behavior and
must not be described as filesystem-isolated.

Subprocesses receive a small runtime baseline plus explicitly declared
credential and environment allowlists. They no longer inherit `os.environ`.
Captured diagnostics are redacted before being returned for persistence.

The orchestrator reaches the lifecycle through a compatibility adapter.
`run_session()` remains available on the v0.2 built-ins, and third-party v0.2
backends exposing only that method remain accepted. Unit 3 does not add
governed admission; that remains Unit 7 scope.
